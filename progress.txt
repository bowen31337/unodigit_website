## Codebase patterns an implementer must know

- Monorepo: pnpm workspace + Turbo 2. Worker at apps/ba-bot-api, shared wire
  types at packages/ba-bot-contract, Next site at apps/web.
- `pnpm test -- <name>` does NOT narrow under vitest 4. Run the full suite (~2s).
- Tests: `import { env, exports } from 'cloudflare:workers'`; invoke via
  `exports.default.fetch(input, init?)` — pre-bound, no env/ctx args.
  `cloudflare:test` is deprecated for `env` (still correct for applyD1Migrations).
- Mocks MUST build Response lazily: `mockImplementation(async () => new Response(...))`.
  The eager `mockResolvedValue(new Response(...))` fails under workerd with
  "Cannot perform I/O on behalf of a different request".
- `step()` returns `slots`/`forcedAdvances` BY REFERENCE when unchanged. Never
  push or assign into them; always spread.
- Session persistence goes through `persistSession()` in src/session.ts, which
  writes KV and D1 together. Writing only one is a defect class already fixed
  twice; do not reintroduce it.
- D1 enforces foreign keys (PRAGMA foreign_keys = 1). Ordering matters: check a
  row exists before writing anything that references it.

## Constraints that are not negotiable

- NO lead field (name, email) may reach src/llm/, src/graph/prompts.ts, or
  src/estimator/. DeepSeek is hosted in China; Australian Privacy Act APP 8 makes
  this the highest-consequence constraint in the project.
  Guard: grep -rnE "\b(name|email)\b" src/llm/ src/graph/prompts.ts src/estimator/
  must return only the prompt line telling the model NOT to ask.
- The frozen system prompts must stay byte-identical across requests. No
  timestamps, ids, or interpolation — DeepSeek's prefix cache is a byte match and
  ~98% cheaper on hits.
- Test output must stay pristine. Zero warnings.

### 2026-08-19 — US-004a: oversized first passes can now reach program mode

CONTROLLER RULING, not a plan task. Plan 2 has no Task 4a; this fixes a defect
found reviewing US-004.

Defect. The spec (design doc ~line 245) says "when the first-pass estimate
exceeds 300 tasks, the estimator re-runs in program mode", with no upper bound.
But US-001's contract capped single-mode total_tasks and EstimateCategorySchema
.bullets at max(400), and runEstimate only reaches the program pass via
`first.shape.total_tasks > programThreshold` — which requires the first pass to
have VALIDATED. So a project the model sized over 400 failed schema validation,
burned its one repair retry, and returned {ok:false, reason:'parse'}; program
mode never fired. Program mode worked across a 100-task window (301-400) while
the failure zone above 400 was unbounded — and the frozen prompt steers into it
("platforms are larger"). Program-mode total_tasks already had NO max, which is
the tell: large numbers were always meant to live there.

Ruling: spec beats plan. Raised the single-mode ceilings so an oversized first
pass is representable and can route to the program pass:
- EstimateCategorySchema.bullets: max(400) -> max(2000)
- single-mode total_tasks:        max(400) -> max(2000)
- SubsystemSchema.total_tasks:    UNCHANGED at max(400) — the spec targets
  80-250 tasks per subsystem, so 400 is a correct per-subsystem bound.
Frozen ESTIMATOR_SYSTEM_PROMPT, PROGRAM_MODE_ADDENDUM and CALIBRATION are
byte-unchanged (verified by empty `git diff --stat` on those paths). Cost if the
ruling is wrong: one small revert.

Second defect, found while making the first and caused to widen by it.
totalsAgree() in program mode summed ALL subsystem category bullets and compared
that to the UMBRELLA total. It never checked that a subsystem's own categories
sum to its own total_tasks. So one subsystem could overstate and another
understate, netting out to a valid grand total. Previously bounded (categories
capped at 400); raising to 2000 widened it, and US-005's renderer prints
per-subsystem totals as delivery phases, so an inconsistent subsystem becomes a
phase whose task count contradicts its own breakdown. totalsAgree now requires
each subsystem to agree with itself, then sums subsystem totals against the
umbrella.

apps/ba-bot-api and packages/ba-bot-contract typecheck exit 0. RED was confirmed
for BOTH fixes by reverting the source and re-running, not by assertion:
- ceiling: with max(400) restored, exactly one test failed — the 600-task first
  pass returned ok:false, never reaching program mode.
- per-subsystem: with the old totalsAgree restored, the self-contradictory shape

Note for a later story, NOT fixed here: askOnce uses maxTokens 1600. A

### 2026-08-19 — US-007: POST /api/generate orchestration

Created src/api/generate.ts (registerGenerateRoutes + an exported
endConversation), registered it in src/index.ts, and added
QUOTE_LINK_SIGNING_KEY / RESEND_API_KEY to Env — declared only, deliberately NOT
added to index.ts's REQUIRED_SECRETS, since nothing reads them yet and a 503 on
their absence would take the whole API down for a feature that does not exist.
Task 7 of the plan carries no literal code, so this is the first story written
rather than transcribed.

Order of checks, and one deliberate deviation from the plan's stated order:
404 unknown conversation -> IDEMPOTENCY -> 409 wrong_state -> brief ->
rate limit -> estimate -> price/render/persist -> advance to DONE -> close the
conversation row. The plan lists idempotency third, after the 409. That order is
wrong in practice: a successful generate leaves the session at DONE, so a
refresh or a double-click would be answered 409 rather than the brief the
visitor already paid for — contradicting the plan's own acceptance criterion
that "an existing brief for the conversation is returned". Checking the brief
first satisfies both criteria: the 409 case (mid-interview, no brief) is
unaffected, because only this route ever writes a brief.

Second judgement call: a below-floor project still returns its Quote object and
still persists the quote row. GenerateResponseSchema's doc comment in the
contract says quote is "absent when the rate limit was hit or the project priced
below the engagement floor", but the plan's step 7 prices/persists
unconditionally and its step 10 lists below-floor as a HEADLINE variant
alongside book-a-call and estimator-failed — i.e. a quote that exists but is
presented differently. renderQuote already suppresses the band and the per-task
rate for belowFloor, so the artifact is safe; returning null would leave a
non-null quoteId pointing at a row the client cannot see. The contract comment
is prose, not schema, and is now slightly stale.

`belowFloor` is NOT a column on `quotes`, so the idempotent re-read cannot load
it. quoteFromRow re-derives it with the same rule priceQuote used
(weighted * rate < MINIMUM_ENGAGEMENT_AUD). Everything else comes straight off
the row. This is the one place in the codebase that re-derives rather than
reads; a below_floor column would remove it, at the cost of a migration.

Beyond the plan's step list, deliberately: the estimate's promptTokens /
completionTokens are added to conversations.tokens_in/tokens_out via the same
UPDATE chat.ts uses. The heavy model is the most expensive call in the app and
omitting it would leave that spend invisible in the very columns that track the
cheap one. Asserted in the happy-path test (900/400), so it is not untested
scope.

### 2026-08-19 — US-008: HMAC-signed quote retrieval

Created src/util/sign.ts (signId/verifyId, HMAC-SHA256 hex over the quote id
via WebCrypto — no dependency added) and src/api/quote.ts
(GET /api/quote/:id?sig=...), registered in src/index.ts. Task 8 of the plan

Constant time. verifyId delegates the MAC comparison to `crypto.subtle.verify`.
The only equality in the function is `bytes === null` on the hex-decode result,
which tests a public structural property of attacker-supplied input, never
secret material. `grep -nE "===|!==|localeCompare" src/util/sign.ts
src/api/quote.ts` returns four lines: two inside doc comments, `hex.length === 0
|| hex.length % 2 !== 0` (public length), and that null-check.

This property has NO observable behaviour — `sig === expected` and
crypto.subtle.verify return identical booleans for every input and differ only
in how long they take. Proven, not assumed: replacing verifyId's body with
`toHex(bytes) === (await signId(id, key))` left ALL 147 behavioural tests green.
So it is pinned structurally, against `verifyId.toString()` with comments
stripped — must contain 'crypto.subtle.verify', must not mention signId, must
contain no `[=!]==?` beyond the decode null-check. Re-running the same mutation
then failed all three. A `?raw` import of the source also works but matches the
word "===" in the file's own doc comments; toString sees only the shipped
function body. If a future refactor moves fromHex's guard, update the one
allowlisted `bytes === null` string in the test rather than deleting the check.

Length safety. fromHex returns null (never throws) for empty, odd-length or
non-hex input. Wrong-but-decodable lengths are deliberately NOT rejected there —
they go to crypto.subtle.verify, which returns false on a length mismatch
without throwing, keeping the comparison on the constant-time path. verifyId
also wraps the verify in try/catch: an unhandled throw becomes a 500, and a 500
is its own oracle telling an attacker their input was structurally interesting.
That catch is load-bearing, not decorative — WebCrypto rejects a zero-length
HMAC key ("Imported HMAC key length (0) must be a non-zero value..."), so an
unconfigured Worker throws inside importKey; the catch turns that into a
fail-CLOSED false. Deleting the try/catch fails exactly one test.

Enumerability. Bad signature and unknown id return the SAME status and the SAME
body: `{"error":"forbidden"}`, 403. A 404-for-unknown split would let an
attacker learn which ids exist from the status alone, and the ids are the entire
access-control mechanism. The test asserts byte identity
(`expect(await unknown.text()).toBe(await badSig.text())`), not "both are 403" —
a mutant returning 403 with `{"error":"not_found"}` fails it. The unknown-id
case is signed with the REAL key so verification passes and the miss can only
come from the D1 lookup; signing it with a wrong key would have exercised the
signature branch and tested nothing.

Verification happens BEFORE the D1 read, on purpose. Doing the lookup first
would let an unauthenticated caller drive D1 with arbitrary ids and buys no
timing symmetry that matters: producing a valid signature for an id you do not
already hold a link to requires the key, so the only branch an attacker can
reach ends at the same 403 with no query. The timing difference distinguishes
"your signature was wrong" from "your signature was right but the id is
unknown", which is not an existence oracle for anyone who cannot sign.

quoteFromRow is now EXPORTED from src/api/generate.ts and imported by quote.ts
rather than copied. belowFloor is re-derived (it is not a column) and that
re-derivation is already a recorded latent defect — US-007 controller notes. One

## The P3 gate — architectural, not a convenience

Spec section 12 requires TWO Cloudflare Access applications and says why one is
not enough: the dashboard is a static page calling the Worker from the browser,
so protecting only the Pages route leaves the admin API open to anyone who knows
the URL. The second application must front the Worker's hostname.

Cloudflare Access CANNOT protect a workers.dev hostname — it injects
Cf-Access-Jwt-Assertion only for hostnames it proxies, which requires an active
zone. SETUP.md records that unodigit.com.au is not one: its DNS is at
OnlyDomains, and a CNAME to *.workers.dev does not route to a Worker because
dispatch matches the Host header against a configured route.

So until the zone moves there is NO way to authenticate the admin API that does
not contradict the spec's own reasoning ("hand-rolled auth would be the most
likely source of a security incident in the project"). Do NOT work around this
with a shared bearer secret, an allowlisted header, or a signed cookie. Stop at
the gate and report.

## Deploy hazard carried in

### 2026-08-19 — RULING: admin surface is scripts, not an Access-gated web API

User asked why P3 was needed. Investigated rather than restating it, and the
verified DNS position is:

  NS unodigit.com.au  -> ns1/2/3.onlydomains.com    (zone NOT on Cloudflare)
  www.unodigit.com.au -> CNAME uno-digit.pages.dev  (Pages custom domain)
  server: cloudflare, cf-ray present                (traffic IS proxied)

The site is SERVED by Cloudflare but the domain is not MANAGED by Cloudflare.
Access applications are configured per-zone in Zero Trust and attach to a
hostname in a zone on your account; a CNAME-only Pages custom domain gives
proxying, not a zone. `unodigit-ba-bot.unodigit.workers.dev` belongs to
Cloudflare's zone, not ours. So spec section 12's second Access application has
nothing to attach to, and US-004 would have verified a JWT that never arrives.

That constraint is real, but it only binds the spec's DESIGN. The underlying
requirements are: see leads and funnel, read briefs and quotes, and delete a
lead on request (Privacy Act, spec section 8). A browser dashboard is one way to
meet them, not the only way.

RULING (user-approved): meet them with scripts over
`wrangler d1 execute ba_bot --remote`, authenticated by the Cloudflare API token
already in 1Password. Zero new auth surface, no new HTTP endpoint to secure, no
DNS move — and it unblocks the Privacy Act deletion path TODAY rather than after
a nameserver migration.

This is a deliberate deviation from spec section 12. US-004 through US-008 are
marked deferred, not abandoned; revisit only if a browser dashboard is still
wanted after the scripts are in use. If it is, P3 is still the prerequisite and
the analysis above still holds.

Cost if wrong: the scripts are ~200 lines of shell and are thrown away, having
in the meantime provided lead visibility and a legally-required deletion path.

Note for whoever does move the DNS: the risk is NOT the Cloudflare side. Moving
nameservers hands Cloudflare ALL DNS for the domain, including MX. Copy every
existing record — MX, SPF/DKIM TXT, any CNAME/A in use — into the Cloudflare
zone BEFORE switching NS at OnlyDomains, or email stops. Moving also unblocks
P2, since Resend's SPF/DKIM records would then be managed in the same place.

DELETION ORDER, derived from the REFERENCES clauses in 0001_initial.sql
(conversations.lead_id→leads, messages/briefs/events.conversation_id→
conversations, quotes.brief_id→briefs):

  quotes → briefs → messages → events → conversations → leads

The order is about REACHABILITY as much as foreign keys. Delete the
conversations rows first and there is no path left to that lead's messages,
briefs or events — they would sit orphaned in the database forever. Bottom-up
is what makes the cascade complete.

rate_limit and rate_limit_turns are deliberately NOT deleted. They hold salted
SHA-256 of an IP, which is not personal information, and they are the only
meter on DeepSeek spend. If deletion cleared them, "delete my data" would
double as a quota reset and an abuser would ask for it daily. The lead's own
ip_hash column is on the leads row and goes with it.

VERIFIED against a local miniflare D1, never against production. Migrations
applied with `wrangler d1 migrations apply ba_bot --local`, then a fixture of
three leads with rows in every table. `BA_BOT_D1_LOCAL=1` (an env var, not a
flag, so it cannot be reached by a typo) points the scripts at it.
  - --dry-run: full row-count snapshot before and after was byte-identical.
  - real run on the ordinary lead: leads 3→2, conversations 5→3, messages 6→3,
    briefs 4→2, quotes 4→2; rate_limit 2→2 and rate_limit_turns 2→2 INTACT.
  - the second lead and an unrelated lead-less conversation survived untouched.

company of  Evil' Corp . Deleting it removed exactly that lead and left the
